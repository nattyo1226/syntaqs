# Semantic API decisions

## Policy and precedence

The [semantic refactoring plan](semantic-refactoring.md) records the implemented file organization and temporary compatibility paths. Final API cleanup and preludes remain deferred.

The user chose semantic module paths as the canonical public API and permits public re-exports only in `prelude`. The [recommendations](module-api-recommendations.md) are design input; their suggestions to use semantic `pub use` outside preludes do not override that choice. Public items are defined in their canonical module, including when this requires moving definitions. A type alias defining a concept is not a re-export. Internal `use` and restricted-visibility imports are unaffected.

Crate roots are themselves meaningful namespaces: central crate-wide abstractions may be defined there without a redundant module. The user requested a prelude as a convenient entry point; provide one per public library crate, including small crates, with a deliberately limited selection. Prelude exports are public API too.

These decisions describe the later API direction. The [execution plan](README.md) defers the full public-item inventory, broad API reorganization and prelude selection until after module organization. Some file moves are implemented, but the public paths below are not a complete or validated final API. Preserve public functionality and observable behavior; permitted path changes do not imply permission to remove public types.

## Decided canonical boundaries

- **core:** Rename `ops` to `algebra` and `expr` to `expression`. Define `Product`, `Act`, `Adjoint`, `Identity`, `Trace`, `InnerProduct`, and the current parity abstractions directly in `algebra`; keep grading there unless its scope later warrants a child module. Define `Dimension` and `DimensionOverflow` in `space`. `Dimension` is implemented by primitive types and describes the dimension of their spanned state or operator space, independently of a chosen basis. The `space` namespace therefore covers both state-space and operator-space dimensional concepts; basis enumeration and `HilbertSpace` queries both use them. Keep `system` and `coefficient` as independent concepts. Treat `LinearCombination` and `Term` as low-level syntax components, alongside the existing expression parts; retain their semantics and determine the precise canonical paths together with the remaining expression structure. Keep `expression::local` and `expression::composite` for their respective types, with `ExpressionError` in `expression` because it crosses expression operations. Keep the existing low-level public syntax container capabilities accessible under `expression::parts` with coherent child modules; do not silently make previously public types private. Keep evaluation, traversal, formatting, and grouping implementation private. Put `Basis`, `BasisError`, `Coordinates`, `dim_state`, and `dim_op` in `basis`, and keep enumeration/expansion machinery private: these are all basis-facing concepts, while `space::DimensionOverflow` captures the shared failure.
- **basic:** Keep `Id128` and `Tag` defined at the crate root. The crate itself is the meaningful namespace; the earlier proposed `index` module adds no useful distinction.
- **geometry:** Use public `geometry`, `relation`, and `mapping` namespaces. Rename `connection` to `mapping`; it maps sites and groups to data rather than representing a differential-geometric connection. Define `Geometry` and `Boundary` in `geometry`, and `Chain` in `geometry::chain`. Define `Relation`, `SiteGroup`, and `SiteGroupError` in `relation`; keep `Consecutive` and its error in `relation::consecutive`, and `NearestNeighbors` in `relation::nearest_neighbor`. This preserves meaningful children without the recommendation's parent re-exports. Put mapping types and `MappingError` in `mapping`.
- **normalize:** Expose `norm::{Norm, Normalize}` and `expectation::{NormalizedExpectation, NormalizedExpectationIn}`. Define `NormalizationError` at the crate root because it is shared by both responsibilities.
- **export:** Define the central `Export`, `Exported`, and shared `ExportError` at the crate root. Define `VectorMetadata` in public `vector`; define `MatrixArgs`, `MatrixMetadata`, and `Layout` in public `matrix`. Existing vector/matrix implementation can coexist there with restricted visibility, or move to private children as useful; keep backend and coordinate extraction internals private. Remove third-party `ndarray`/`sprs` re-exports under the agreed policy, update consumers to direct dependencies, and preserve feature-gated export support.
- **lie:** Expose `family`, `representation`, `invariant`, `decomposition`, and `numerical` as semantic domains. Place family transformation responsibilities, including `FamilyTransform` and `OrthonormalityReport`, under `family` and move their implementation file from `src/transform.rs` to `src/family/transform.rs`. Retain `family::validation` and `family::projection` for their coherent subdomains; exact public paths are subject to later API review. Place all numerical configuration, tolerances, and numerical errors, including `NumericalOptions`, `Tolerance`, `ToleranceCheck`, and `NumericalError`, under `numerical`; split implementation files within `numerical/` if keeping them together would make a file unwieldy. Keep numerical kernels restricted. Define the general `FamilyExpression`, `lie_bracket`, and `LieError` at the crate root. Keep decomposition spectral machinery private and maintain access to all public diagnostic/result types.
- **physical systems:** Keep the `SpinHalf`, `SpinOne`, and `Fermion` aliases at their respective crate roots; they identify the crate's system. Retain public `basis`, `operator`, `state`, and `models` consistently across all three crates, with private coefficient helpers. Keep `models` plural to match existing names. The dedicated spin-half Neel constructor has been removed, and the Heisenberg example constructs its alternating product state from expression building blocks. The three physical-system errors are now `models::ModelError` without root re-exports; their variants and source behavior are retained.

`parts::sum`, `parts::scale`, and `parts::operation` remain the planned syntax-container split, not a reason to change the contracts of existing public types. Existing crate-root definitions such as system aliases are not re-exports and remain valid. Preserve feature gates, `no_std` requirements, and public signatures apart from approved path changes.

The core algebra, grading, and dimension placement above have been agreed. The rename from `expr` to `expression` and the treatment of `LinearCombination` and `Term` as low-level syntax components have also been agreed; precise paths and remaining expression boundaries remain subject to discussion. For geometry, placing `Boundary` under `geometry`, placing `SiteGroup` under `relation`, and renaming `connection` to `mapping` have been agreed; exact public paths remain for the later API review. For export, grouping matrix-specific arguments and metadata under `matrix` and vector metadata under `vector` has been agreed; `Exported` and the shared error remain crate-wide concepts. Public paths and external dependency re-exports remain for the later API review. For Lie, family transformations belong under `family`, with implementation files in the `family/` directory. Numerical configuration, tolerances, and numerical errors belong under `numerical`, with files split if needed. Exact public paths remain for the later API review. Other topics remain subject to discussion.

## Expression, export and numerical file layout

The core, export, and numerical file layouts below are agreed. Module visibility and canonical public paths remain for the subsequent API review; a file layout alone does not authorize parent-module public re-exports.

- **core expression parts:** keep `expression/parts/linear_combination.rs` for `LinearCombination`, `Term`, and `IntoTerms`, `sum.rs` for `SumExpr` and its owning iterator, `scale.rs` for `ScaleExpr`, and `operation.rs` for product, action, and adjoint syntax. Rename the enclosing `expr` module to `expression` as agreed. The existing split already has these child files.
- **export:** keep `matrix.rs` and `vector.rs` as thin module entry points. Under `matrix/`, separate arguments (`args.rs`), matrix metadata and layout (`metadata.rs`), and conversion implementations (`export.rs`). Keep the matrix-specific internal `Ambient` trait with the arguments or conversion implementation according to its access needs. Under `vector/`, separate vector metadata (`metadata.rs`) and conversion implementations (`export.rs`).
- **lie numerical:** keep `numerical.rs` as a thin module entry point. Under `numerical/`, separate tolerances (`tolerance.rs`), numerical options (`options.rs`), numerical errors (`error.rs`), and internal calculation kernels (`kernels.rs`). Move the existing kernel tests under `numerical/kernels/tests.rs`. Keep `LieError` outside `numerical`, as it also covers non-numerical failures. Assess shared validation helper placement while implementing.

These layouts preserve existing behavior and test coverage. The new child modules' visibility, resulting canonical paths, and prelude membership are not determined by these file names.

## Decisions deferred until after module organization

1. **Exact public item inventory and paths:** inspect every current public item, including iterator types, aliases, associated types and externally reachable signature types; assign any not listed above and check that no previously public capability becomes unreachable. Resolve the precise location of `ExpressionError` and `LinearCombination` implementation with the planned children without exposing implementation solely for Rust visibility.
2. **Exact prelude members:** inspect real example and test usage, select explicit items from each crate's canonical paths, and test common combinations for wildcard conflicts. Avoid wholesale exports, cross-crate convenience exports, and speculative configuration types. A small crate's prelude may intentionally contain only its principal types.
3. **Detailed implementation boundaries:** determine visibility and placement for shared helpers without exposing internals. Confirm the planned file splits through implementation and rustdoc checks.

## Neel removal and integration tests

The Heisenberg example constructs a Neel state from alternating primitive states placed on the existing factor spaces. Former constructor calls in `crates/syntaqs-spin-half/tests/systems.rs` and `examples/tests/chain.rs` have been replaced with expression building blocks.

Integration tests use simpler product states where alternation is incidental, and construct alternating basis states for analytic Neel energy and export checks. Hamiltonian construction, evaluation, empty and grouped spaces, boundaries, feature-gated exports and model error handling remain covered. Constructor-only assertions and capability checks were removed; no public Neel helper was added.
