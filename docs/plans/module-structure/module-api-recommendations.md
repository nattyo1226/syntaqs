# Semantic Module Organization and Public API Design

**Project:** syntaqs
**Baseline:** `v5` branch
**Status:** Design Proposal

## 1. Overview

This document proposes a consistent module organization and public API policy for the `syntaqs` workspace.

The central principle is that **the public module hierarchy should reflect the semantic structure of the library rather than its implementation details**.

Each crate should represent a coherent domain of responsibility, and its public modules should correspond to meaningful subdivisions of that domain.

Public APIs should be accessible through semantically appropriate module paths. A `prelude` may provide convenient shortcuts for frequently used types and traits without replacing the canonical module hierarchy.

The proposal largely preserves the existing crate boundaries while refining module responsibilities, naming conventions, and public visibility.

## 2. Design Principles

### 2.1 Semantic Organization

Crates and modules should be organized according to the mathematical or physical concepts they represent.

A public module should satisfy at least one of the following criteria:

- It represents a distinct concept within the crate's domain.
- It groups a coherent family of related types, traits, or operations.
- It defines a meaningful namespace that can remain stable as implementations evolve.

Implementation details should not determine the public module hierarchy.

Internal modules may be organized differently from public modules when necessary.

### 2.2 Canonical API Paths

Each public item should have a canonical path that reflects its semantic ownership.

For example:

```rust
use syntaqs_core::expression::LinearCombination;
use syntaqs_core::algebra::Adjoint;
use syntaqs_geometry::relation::NearestNeighbors;
```

Public items should not be indiscriminately re-exported at crate roots.

Re-exports remain appropriate when they establish semantic ownership or provide explicitly documented convenience APIs.

### 2.3 Crate Root Responsibilities

A crate root is itself a meaningful namespace.

Items representing the central abstraction or identity of an entire crate may be defined directly at its root.

For example:

```rust
syntaqs_export::Export
syntaqs_spin_half::SpinHalf
syntaqs_spin_one::SpinOne
syntaqs_fermion::Fermion
```

These paths are preferable to introducing redundant modules solely to enforce a uniform hierarchy.

### 2.4 Prelude Modules

Each crate may provide a `prelude` containing commonly used types and traits.

For example:

```rust
use syntaqs_core::prelude::*;
use syntaqs_spin_half::prelude::*;
```

A prelude is a convenience interface, not the canonical API.

Its contents should be deliberately selected rather than generated by re-exporting the entire public API.

In particular:

- Frequently used traits are strong candidates for inclusion.
- Commonly instantiated types may be included.
- Specialized analysis types and configuration structures should generally remain accessible through explicit paths.
- Wildcard import conflicts between different preludes should be considered.

A crate should not be required to provide a prelude if its API is sufficiently small.

### 2.5 Visibility Policy

The following conventions are recommended:

| Visibility | Intended use |
|---|---|
| `pub` | Stable public API |
| `pub(crate)` | Shared implementation details within a crate |
| Private | Internal implementation details |
| `pub use` | Semantically justified re-exports and preludes |

Public visibility should be treated as an API commitment.

In particular, implementation-oriented modules should not be made public merely because they contain public types.

### 2.6 Avoid Unnecessary Hierarchy

Semantic organization does not require every type to reside in a nested module.

A module should be introduced only when it contributes a meaningful distinction.

For example, creating an `index` module inside `syntaqs-basic` may add little value if the crate itself already serves that purpose.

Similarly, a single operation does not necessarily justify a dedicated public module.

## 3. Proposed Module Organization

### 3.1 `syntaqs-core`

`syntaqs-core` defines the fundamental abstractions for quantum systems, algebraic operations, Hilbert spaces, and symbolic expressions.

Proposed organization:

```text
syntaqs-core
├── algebra
│   ├── grading
│   ├── Product
│   ├── Act
│   ├── Adjoint
│   ├── Identity
│   ├── Trace
│   └── InnerProduct
├── basis
├── coefficient
├── expression
│   ├── local
│   ├── composite
│   ├── LinearCombination
│   ├── Term
│   └── ExpressionError
├── space
│   ├── Dimension
│   ├── HilbertSpace
│   ├── TensorKind
│   └── SpaceError
├── system
│   ├── QuantumSystem
│   ├── ExpressionFactory
│   └── ...
└── prelude
```

**Algebraic operations**

Rename `ops` to `algebra`.

The current operations describe algebraic capabilities and structures rather than implementation-level operations.

The traits `Product`, `Act`, `Adjoint`, `Identity`, `Trace`, and `InnerProduct` therefore belong naturally to `algebra`.

Parity-related abstractions may be organized under `algebra::grading` if the graded-algebra API grows sufficiently large. Otherwise, they may remain directly under `algebra`.

`Dimension` should be associated with `space`, as it describes the dimensional properties of the underlying spaces.

**Expressions**

Rename `expr` to `expression`.

The `expression` module should contain symbolic representations of algebraic expressions, including local and composite states and operators.

In particular, `LinearCombination` should remain within `expression`.

The current `LinearCombination<P, C>` represents a formal linear combination,

\[
\sum_i c_i p_i,
\]

without necessarily identifying algebraically equivalent expressions.

For example, it does not inherently normalize repeated terms or enforce a canonical representation of the corresponding free-module element.

Its primary responsibility is therefore symbolic expression representation rather than the implementation of an abstract algebraic structure.

The recommended canonical path is:

```rust
syntaqs_core::expression::LinearCombination
```

The `Term` type also belongs to this module.

Low-level expression containers such as `SumExpr`, `ScaleExpr`, and `ProductExpr` may remain private unless independently useful as public abstractions.

The `local` and `composite` modules should expose the corresponding expression types if these categories remain meaningful in the public API.

**Quantum systems**

Retain `system` as an independent module.

`QuantumSystem`, `ExpressionFactory`, and their associated type aliases collectively define how primitive states, operators, and coefficient types form a quantum system.

This responsibility is distinct from the representation of individual expressions.

**Error types**

Error types should generally reside alongside the operations or concepts that produce them.

A dedicated public `error` module should not be required merely to collect unrelated error types.

Shared errors that genuinely apply to an entire crate may remain at the crate root.

### 3.2 `syntaqs-basic`

Retain the existing flat structure.

```text
syntaqs-basic
├── Id128
└── Tag
```

The crate is sufficiently small that additional module hierarchy would provide little semantic value.

Both types serve related identification purposes, and the crate boundary already provides an appropriate namespace.

No structural change is necessary.

### 3.3 `syntaqs-geometry`

Organize the public API around three responsibilities:

1. Geometric structures.
2. Relations between sites.
3. Mapping relations to associated data.

Proposed organization:

```text
syntaqs-geometry
├── geometry
│   ├── Geometry
│   ├── Chain
│   └── Boundary
├── relation
│   ├── Relation
│   ├── Consecutive
│   ├── NearestNeighbors
│   ├── SiteGroup
│   └── ...
├── mapping
│   ├── SiteMapper
│   ├── MappedGroup
│   ├── MappedGroupResult
│   └── MappingError
└── prelude
```

**Geometry**

`Geometry`, `Chain`, and `Boundary` belong to the same conceptual domain.

`Boundary` describes a property of a geometric structure and does not necessarily require an independent public module.

**Relations**

`Relation` and its concrete implementations describe how groups of sites are selected or related within a geometry.

`SiteGroup` also belongs to this domain because it represents the resulting groups of sites.

**Mapping**

Rename `connection` to `mapping`.

The existing functionality associates sites or site groups with external data. The term `mapping` describes this responsibility more precisely.

Additionally, `connection` has an established mathematical meaning in differential geometry that may be misleading in this context.

### 3.4 `syntaqs-normalize`

The existing internal division is already semantically appropriate.

Proposed organization:

```text
syntaqs-normalize
├── norm
│   ├── Norm
│   └── Normalize
├── expectation
│   ├── NormalizedExpectation
│   └── NormalizedExpectationIn
├── NormalizationError
└── prelude
```

The `norm` module concerns norms and normalization operations.

The `expectation` module concerns normalized expectation values.

`NormalizationError` may remain at the crate root if it represents failures shared across both domains.

The principal change is to expose the existing conceptual modules directly rather than flattening their contents into the crate root.

### 3.5 `syntaqs-export`

Distinguish general export abstractions from representation-specific configuration.

Proposed organization:

```text
syntaqs-export
├── Export
├── Exported
├── ExportError
├── vector
│   └── VectorMetadata
├── matrix
│   ├── MatrixArgs
│   ├── MatrixMetadata
│   └── Layout
├── prelude
└── internal backend modules
```

`Export` and `Exported` represent the central abstractions of the crate and should remain at its root.

Vector- and matrix-specific configuration and metadata belong to their respective modules.

Backend implementation modules should remain private unless they expose meaningful, independently supported extension interfaces.

Existing feature-dependent re-exports of external crates, such as `ndarray` and `sprs`, should be evaluated separately. They are dependency convenience APIs rather than part of the semantic module hierarchy.

### 3.6 `syntaqs-lie`

Organize the library according to the mathematical objects and analyses it provides.

Proposed organization:

```text
syntaqs-lie
├── FamilyExpression
├── lie_bracket
├── LieError
├── family
│   ├── OperatorFamily
│   ├── FamilyCoordinates
│   ├── FamilyTransform
│   ├── FamilyValidation
│   ├── GramMatrix
│   ├── GramFactorization
│   ├── Projection
│   └── ...
├── representation
│   ├── StructureConstants
│   ├── AdjointRepresentation
│   ├── KillingForm
│   └── ...
├── invariant
│   ├── AdjointCommutant
│   ├── CenterSplit
│   └── ...
├── decomposition
│   ├── LieDecomposition
│   ├── LieComponent
│   ├── DecompositionOptions
│   └── ...
├── numerical
│   ├── NumericalOptions
│   ├── NumericalError
│   ├── Tolerance
│   ├── ToleranceCheck
│   └── ...
└── prelude
```

**Operator families**

Merge the public responsibilities of `family` and `transform`.

`FamilyTransform` describes transformations of operator families and therefore belongs naturally to `family`.

The implementation may remain separated internally.

**Representations**

Retain `representation` for structure constants, adjoint representations, Killing forms, and closely related structures.

**Invariants and decomposition**

Retain `invariant` and `decomposition` as separate public modules.

They represent different mathematical tasks:

- Identifying invariant structures and subspaces.
- Decomposing Lie algebras into constituent structures.

**Numerical configuration**

Consolidate tolerance-related types and numerical configuration under `numerical`.

Internal numerical kernels should remain private.

**Crate-level operations**

Fundamental operations such as `lie_bracket` may remain at the crate root if they are not naturally owned by one of the specialized modules.

Likewise, `LieError` may remain at the root when it represents a crate-wide error type.

### 3.7 Physical-System Crates

The three physical-system crates should follow a shared public structure:

- `syntaqs-spin-half`
- `syntaqs-spin-one`
- `syntaqs-fermion`

Proposed organization:

```text
syntaqs-spin-half
├── SpinHalf<C>
├── basis
├── operator
├── state
├── model
└── prelude

syntaqs-spin-one
├── SpinOne<C>
├── basis
├── operator
├── state
├── model
└── prelude

syntaqs-fermion
├── Fermion<C>
├── basis
├── operator
├── state
├── model
└── prelude
```

**Basis, operator, and state**

Retain these modules as independent public namespaces.

They correspond directly to distinct mathematical and physical concepts:

- `basis`: Basis definitions and representations.
- `operator`: Primitive operators and their algebraic behavior.
- `state`: Primitive states and state-related constructions.

**Physical models**

Retain a dedicated namespace for physical model construction.

Either `model` or `models` is acceptable, provided that the choice is consistent across the three crates.

The existing `models` modules contain both Hamiltonian constructors and, in some cases, state constructors.

These responsibilities should be examined separately.

A possible long-term organization is:

```text
model
├── Hamiltonian constructors
└── ModelError

state
├── Primitive state definitions
└── Common state constructors
```

In particular, a Néel-state constructor belongs semantically to state construction rather than Hamiltonian model construction.

However, this separation should not require unnecessary changes to existing factory abstractions.

**Crate-level system aliases**

Keep the principal system aliases at the crate roots:

```rust
syntaqs_spin_half::SpinHalf<C>
syntaqs_spin_one::SpinOne<C>
syntaqs_fermion::Fermion<C>
```

These aliases represent the corresponding physical systems as a whole.

**Error naming**

Replace ambiguous names such as `UtilityError` with names that communicate the relevant responsibility, such as `ModelError`.

Error types should be located within the modules that own the corresponding operations.

## 4. Prelude Policy

A prelude should provide convenient access to the most frequently used items without obscuring the canonical module hierarchy.

For example, the physical-system crates may expose:

```rust
pub mod prelude {
    pub use crate::SpinHalf;

    pub use crate::basis::{
        CartesianBasis,
        LadderBasis,
        SzBasis,
    };

    pub use crate::operator::SpinHalfOperator;
    pub use crate::state::SpinHalfState;
}
```

The equivalent policy should apply to `syntaqs-spin-one` and `syntaqs-fermion`.

For `syntaqs-core`, frequently used algebraic traits are particularly suitable for a prelude:

```rust
pub mod prelude {
    pub use crate::algebra::{
        Act,
        Adjoint,
        InnerProduct,
        Product,
        Trace,
    };

    pub use crate::basis::Basis;
    pub use crate::space::HilbertSpace;
    pub use crate::system::QuantumSystem;
}
```

The precise contents should be determined by actual usage rather than an attempt to include every publicly available item.

Where possible, each crate's prelude should initially contain only items owned by that crate.

Cross-crate convenience re-exports may be introduced later if they demonstrate clear practical value.

## 5. Implementation Strategy

The proposed changes should be introduced incrementally.

### Phase 1: Establish Semantic Boundaries

Document the responsibility of each crate and public module.

Identify modules whose current names describe implementation details rather than mathematical concepts.

Resolve ambiguous ownership before changing visibility.

### Phase 2: Reorganize Public Modules

Introduce the proposed semantic module paths.

Prefer `pub use` inside the appropriate semantic modules when an implementation can remain in its existing location.

Avoid unnecessary file movement or implementation changes.

### Phase 3: Consolidate Public APIs

Remove redundant crate-root re-exports where they no longer serve as canonical APIs.

Keep central crate-level abstractions at their roots.

Move error types into appropriate semantic namespaces when justified.

Changes to existing public paths should be treated as potentially breaking API changes.

### Phase 4: Introduce Preludes

Add narrowly scoped `prelude` modules.

Select their contents based on common usage patterns.

Avoid using preludes as a substitute for a well-designed public module hierarchy.

### Phase 5: Validate the Result

Evaluate the revised structure against the following criteria:

- Each public item has a clearly identifiable semantic owner.
- Public paths are predictable across related crates.
- Internal implementation changes do not unnecessarily affect public APIs.
- Related crates use consistent module naming.
- Prelude imports remain convenient without causing excessive name collisions.
- Documentation consistently presents canonical API paths.
- Existing usage examples can be expressed naturally with the revised hierarchy.

## 6. Summary of Recommended Changes

| Crate | Recommended action |
|---|---|
| `syntaqs-core` | Rename `ops` to `algebra`; restructure `expr` as `expression`; retain `LinearCombination` under `expression`. |
| `syntaqs-basic` | Preserve the existing flat API. |
| `syntaqs-geometry` | Organize the API into `geometry`, `relation`, and `mapping`. |
| `syntaqs-normalize` | Expose `norm` and `expectation` as semantic namespaces. |
| `syntaqs-export` | Retain general export abstractions at the root; expose representation-specific modules. |
| `syntaqs-lie` | Consolidate family transformations and numerical configuration; preserve the main mathematical subdivisions. |
| `syntaqs-spin-half` | Preserve `basis`, `operator`, and `state`; clarify the responsibility of `models`. |
| `syntaqs-spin-one` | Apply the same organization as `syntaqs-spin-half`. |
| `syntaqs-fermion` | Apply the same organization as the other physical-system crates. |

## 7. Final Recommendation

The public API of `syntaqs` should be treated as a semantic representation of the mathematical and physical concepts implemented by the library.

The recommended policy is:

> **Crate roots represent the central concepts of their respective domains. Public modules represent meaningful subdivisions of those domains. Each public item has a canonical semantic path, while preludes provide optional convenience imports.**

This policy favors conceptual clarity, predictable API organization, and long-term maintainability.

It also avoids two extremes: indiscriminately flattening every public item into a crate root, and introducing unnecessary module hierarchies for concepts that are already adequately represented by their enclosing crates.

The objective is not uniformity of module depth or file structure, but **consistency of semantic ownership across the workspace**.
