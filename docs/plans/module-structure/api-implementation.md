# Public API implementation plan

## Objective and scope

Implement the reviewed public API and preludes in the [API assessment](api-assessment.md). The review is complete; verify its details during implementation. This is a plan, not authorization to change code. Breaking old paths is intentional. Preserve behavior, applicable trait and iterator guarantees, error semantics, feature gates, `no_std`, supported Rust versions, and public capabilities except for the explicitly agreed removals or visibility changes.

The target has public definitions at their agreed semantic module paths, with public re-exports only in each library crate's root `prelude`. Root definitions and semantic aliases remain where agreed. Remove the old core compatibility aliases, parent and root facades, the specified expression parts' public access, and export's third-party re-exports. Do not use another syntaqs crate's prelude within repository crates other than `examples`; this includes their tests, examples and doctests. Update consumers to canonical paths.

## Batch rules

Each numbered stage is a small unit of implementation and verification. Before starting a unit, inspect the worktree, affected definitions, imports, tests and destinations. Preserve unrelated work. Update affected workspace crates, examples, integration tests, doctests and the excluded BLAS fixture as needed for the unit. Test canonical paths from outside the defining crate, not solely through internal imports. Check changes to public signatures and reachable types; do not substitute a test count for behavior coverage. Record results and deviations here.

Core has many downstream consumers. To keep intermediate units buildable, retain an existing public re-export temporarily only when needed for not-yet-migrated callers, and record its removal in the relevant unit. Migrate callers to canonical paths, then remove temporary exports; no compatibility facade remains at completion. Do not retain two independent definitions of one public type. Each completed unit must compile with its affected consumers; avoid a workspace-wide broken intermediate state. If an agreed contract proves infeasible, record the evidence and revise it before proceeding rather than silently narrowing functionality.

## Baseline and migration map

At the stage-0 baseline, `syntaqs-core` exposes `ops` and `expr` as aliases, `algebra::Dimension` and `error::DimensionOverflow` as compatibility re-exports, and core types through root and expression/parts facades. Geometry, normalize, export and Lie expose their current items primarily through crate-root re-exports; physical-system crates re-export their basis and primitive types at root. Basic defines `Id128` and `Tag` at root. No syntaqs prelude use was found in the searched workspace Rust sources. The assessment specifies their target paths and selected preludes.

The intentional removals are the old core compatibility aliases and all non-prelude public facades, public access to the five expression node types and `IntoOperands`, and export's feature-gated `ndarray` and `sprs` re-exports. Existing root definitions and agreed aliases remain definitions, not compatibility facades. For stage 1, retain core's existing root, expression and `expr` paths for still-unmigrated consumers, but remove access to the agreed internal node types as that unit migrates their tests. Remove the remaining core facades and compatibility aliases in stage 2 after updating all workspace consumers. Apply the same temporary-export rule within later units only if needed, recording any such exports and their removal.

`Term<P, C>` currently aliases `ScaleExpr<P, C>`; its public coefficient and operand fields, `LinearCombination::from_terms`, `terms`, `into_terms`, and owned/borrowed `IntoIterator` are used externally. `IntoTerms` aliases `IntoOperands` and currently implements `Iterator`, `DoubleEndedIterator`, `ExactSizeIterator`, and `FusedIterator`; zero and one elements use inline storage, while larger collections can move their allocation. Preserve the applicable behavior without exposing the representation. `Product`, `Act`, `Adjoint` and `Basis` return `LinearCombination`; core `HilbertSpace::leaves` and geometry's `combine_leaves` expose `space::Leaves`. Lie's sealed `FamilyExpression`, diagnostics and error types are used in public bounds and results. Verify these and other reachable associated/signature types as their units migrate.

The direct integration-test uses of `SumExpr` are in core's `linear_combination.rs`; `primitive_contracts.rs` checks legacy/semantic type identity. Move the relevant implementation checks to unit-test ownership and replace obsolete compatibility assertions with canonical/public-behavior checks rather than dropping coverage. Tests elsewhere construct `Term` directly. Current export backends are optional, with no default features; examples and shared tests separately gate related dependencies/features, and the excluded BLAS fixture has its own manifest. In addition to Rust consumers, migrate doctests, READMEs and design documentation at the appropriate stages. Stages 1–9 above specify their targeted checks; rerun searches when applying each unit, because the baseline is not a complete path-by-path migration list.
